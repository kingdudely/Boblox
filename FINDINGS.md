# RbxTransport / WebTransport client — protocol findings

Findings from IDA (`libroblox.so` Android, Windows PE), packet captures of a live
native session, and live join-API experiments. Updated 2026-10-06.

## Join flow (works today)

1. Session: `GET https://users.roblox.com/v1/users/authenticated` (cookies included).
2. Join: `POST https://gamejoin.roblox.com/v2/join-game` with `Accept: text/event-stream`.
   - Body: `{placeId, gameId (universeId), isTeleport:false, gameJoinAttemptId, browserTrackerId,
     playSessionId, eventId, launchData:"", joinAttemptOrigin:"PlayButton"}`.
   - Reply is SSE; `event: ResponseReady` → JSON with `status:2` and **inline `joinScript`**.
   - v1 (`/v1/join-game`) also works but does not always inline the script; `joinScriptUrl`
     (`assetgame.roblox.com/Game/Join.ashx?...`) is single-use and expires quickly.
   - `status:12 "Unable to join Game 211"` was observed intermittently early on and again
     while another session of the same account was active; it resolved later and appears to
     be server-side throttling/eligibility rather than request shape. The extension still
     sends the native default UA `Roblox/WinInet` for `*.roblox.com` API calls via a
     declarativeNetRequest `modifyHeaders` rule (`rules.json`) for fidelity; joins succeed
     with or without it.
3. `joinScript` fields that matter:
   - `NetStackPort` — the RbxTransport/QUIC UDP port.
   - `NetStackConfig` — **percent-encoded JSON**:
     `{"pubKey": "...", "port": <NetStackPort>, "caps": "022dd3ef52ff0892",
       "certHashes": ["<base64 sha256>"]}`.
   - `UdmuxEndpoints: [{Address, Port}]` — public edge IP. The native client sends its UDP
     socket to `Address:Port` (the public/UDMUX endpoint, same numeric port as
     `ServerPort`/`ServerConnections[].Port`), while the RCC address and that same endpoint
     port are carried inside the RUPP TLVs for edge routing. `NetStackPort` is separate
     metadata (native logs it separately and does not use it as the UDP destination).
     We tested raw QUIC against both ports — both are silently dropped.
   - `ServerConnections: [{Address, Port}]` — datacenter-private (10.x) RCC address,
     unreachable from the internet.
   - `GameFqdn` — **currently always null** in production join replies (see below).
   - `TokenValue`, `NetStackTokenValue`, `ClientTicket` — auth material for the transport.

## Transport wire format (from captures of a live native client)

Every game-server UDP packet is **RUPP-wrapped QUIC**:

```
[01][00][u16 BE header_len]
  TLV1: 01 11 02 <16-byte token>
  TLV2: 02 06 <rcc IPv4 (4B)><rcc port (u16 BE)>
[QUIC packet ...]
```

- TLV2 carries the *private datacenter RCC address*; the udmux edge uses it for routing.
- RUPP parse code: `sub_646A4C4` / `sub_646A53C` (client + server).
- The RUPP token rotates during a session (`Switch to new TT token received from RCC`);
  generation goes through `sub_6469FAE` (RuppTokenClientLog2), which delegates to an
  RCC-provided generator object — the token is derived key material, not a fixed join field.
- RUPP init result codes: `0` and `12` both mean accepted (`RtcIoServerPrefixProcessor`),
  everything else drops with "Rupp init failed".
- The server-side accept path `sub_63CFE80`/`sub_63CFB42` also accepts packets with the QUIC
  fixed bit set (`0x40`) directly, skipping RUPP, when the RCC-side
  `RbxTransportPureQuicSupport` flag (`byte_77A01F8`) is on — this is the browser path.
- `DirectServerReturn: true` means replies come from the RCC directly, not via the udmux path.

### Additional native constants (cross-checked against Studio 0.741 RE notes)

- Server-side SNI grammar (`sub_646AD8D`): `{32-hex token}-{8-hex rccIpv4}-{4-hex rccPort}.{vip-hex}.qdmux.roblox.com`.
  Generated by `RbxTransport_PrepareConnectionConfig` (`DebugRbxTransportGenerateGameFqdn`,
  `{}-{}-{}.{}.qdmux.roblox.com`, with `DebugRbxTransportQdmuxVip` as the VIP override).
- Native initial destination CID shape: `0xd1 || rccIpv4 || rccPort u16 BE || 13-byte tail`
  (20 bytes total). Listener logs: `Accepted new connection ... ClientHello SNI='{}' ALPN='{}' caps={} compatMode={}`.
- ALPN in the native RbxTransport path is `RbxTransport` (Studio notes); a browser WebTransport
  can only offer `h3`, so the browser-serving mode must accept `h3` — the `compatMode` in the
  accept log is likely exactly that.
- `*.qdmux.roblox.com` is a delegated DNS zone (NOERROR/NODATA) but has **no records and no
  wildcard** as of 2026-10-06, so the SNI route cannot resolve from a browser yet either.

## Python client status: full native join sequence (2026-10-07)

The Python client now replays the complete native join sequence and gets the server's
full **1857-byte 0x93 join reply byte-identical to the native client's**. Remaining gate:
the server's 0x9B anti-cheat challenge exchange (see below).

### Verified join sequence (client → server, app=4, after QUIC handshake)

1. ctrl stream `app=4 chan=0x6374726C` opened; first message `00 00` ("ctrl hello")
2. `OpenUnreliable` ctrl msgs: `[02][04][chan u32be][wire u32be]` for (3,2), (5,4), (6,6), (11,8)
   (native interleaves these around the early-auth send)
3. stream `app=4 chan=1`: early-auth `a8 11 21 <33B pre> 42 <66B auth>` (from ClientTicket parts 2/3)
4. `0xA7` queue msg: `[a7][u16le count][count × 16B records]` (records are client script hashes; count varies per session)
5. `0x90` client-info msg: flags list + LEB len + JSON (see below)
6. `0x92` nonce: `[92] + LEB(zigzag64((v8<<32) | (v8 ^ 0x63E25F26)))` — v8 random u32
7. `0x8A` join request (see below)
8. `0x8F 00`

Server then sends (server → client):
- ctrl: `OpenUnreliable app=4 chans {3,5,6,11}` wires {3,5,7,9} (allocated fresh each session)
- stream `app=4 chan=1`: `0x93` flag-override message, 1857 B — **byte-identical to native**
- stream `app=6 chan=1`: (dummy/ping channel traffic)
- *native additionally receives* `0x9B` 1962 B challenge → replies 9-byte `0x9B` → "Assigned peer id" (replication starts)

### 0x8A (join request) — exact layout, validated against two captures

```
[0x8A]
LEB(zigzag64(UserId))                 # e.g. 0x22B16F1DE for user 4656429295
LEB(len(ClientTicket)) + ClientTicket # full "ts;b64;b64;b64;17"
u32le(36)
LEB(74) + "2e427f51c4dab762fe9e3471c6cfa1650841723b!6e8e47e92778f00efbb13c7bb151ea88."
LEB(7) + "Android"
LEB(1) + "?"
LEB(v31) + LEB((v31 - 0x0BADF00D) u32)  # v31 = obfuscated xxh32(ClientTicket, seed=1)
0x00                                  # empty string
LEB(len(SessionId-json)) + SessionId-json   # joinScript["SessionId"] verbatim
fe ca 01 c0                           # magic 0xC001CAFE (LE)
```

`v31` derivation (implemented in `py/rbx_client.py: ticket_v31`):
`v31 = (v17 ^ rol32(v29, v30))` where the intermediates are the OLLVM-mixed forms of
`xxh32(ticket, seed=1)` masked against the compile-time constant `S = dword_71941A0 = 0x71375635`
(values `1434170839` [= 0x5579F0D7] and shift/branch bits derived from `v8 = i16(-17506*S)`).
Validated on both captures (v31 == the first LEB value).

### 0x90 (client info) — rebuilt from our join reply

Template: start from a captured 0x90 (flags list prefix is static), replace the JSON with a
rebuild of our own, where only 3 fields are session-bound:
- `RandomSeed1`      ← joinScript["RandomSeed1"]
- `APIsecurityToken` ← joinScript["APIsecurityToken"]
- `__joinTicket`     ← JSON {"SerializedClientFields":…, "EncryptedServerFields":…}
                        both taken verbatim from join reply's `joinTicket`

JSON serialization with `json.dumps(..., separators=(",", ":"))` reproduces native byte-for-byte
(verified: 9302 B exact match).

### 0x9B challenge (the remaining gate)

Native flow: after the 0x93, server sends `0x9B` 1962 B:
`[9b][u32#1][u32#2][u32 len][len-byte blob]` (blob = 1949 B high-entropy data, likely
encrypted/compiled challenge payload). Client replies `[9b][u32#1][u32 answer]` (9 B), where
answer is computed by running the challenge through `GenericChallengeService` (`sub_435D53A`,
"challenge" lookup). It is validated as "Bytecode Auth Check" (`sub_32A0270` k1).

Observed states with our Python client (mocktail stopped):
- stale-ticket replays → server **resets the stream** (rc 0x106) — server validates the joinTicket
- rebuilt 0x90 + fresh 0x92 + our 8A → server sends the 0x93 but does **not** send the 0x9B
  challenge, so replication never starts
- sending **no A7** gets a different 0x93 variant (0x70f prefix, 1811 B) + a new 2-byte/short ctrl
  exchange — A7 affects the server's validation path but is not the challenge trigger
- the server's 0x9B challenge gate is not yet understood; likely tied to the 0x9B/bytecode check
  below, or to the A7 script-hash validation

### Why the browser cannot connect yet


- Chrome's WebTransport emits **raw QUIC**; browsers cannot prepend a RUPP header to UDP
  datagrams. The production edge (udmux) routes on RUPP and **silently drops** RUPP-less UDP.
- Verified experimentally over 2026-10-05/06: Chrome WebTransport and aioquic Initials to live
  `udmuxIP:NetStackPort` and `udmuxIP:ServerPort` (raw, native custom `0xd1` destination CIDs,
  qdmux SNI with the recovered grammar, `h3` and `RbxTransport` ALPNs, real join tokens where
  applicable) are transmitted (packet-captured) and receive **zero** bytes back — while the
  native client on the same machine/host/account plays fine with RUPP framing.
- Independent corroboration: the Studio 0.741 RbxTransport RE notes show the same wall — a
  native-shaped QUIC client still times out at the 10 s handshake budget even with qdmux SNI,
  native CIDs, and RUPP prefixes. This matches the web client not having shipped yet.
- The intended browser-facing edge is visible in the binary: `RbxTransport_PrepareConnectionConfig`
  generates `<token>-<rccIp>-<rccPort>.<vip>.qdmux.roblox.com` and the listener parses that SNI
  (`sub_646AD8D`). `qdmux.roblox.com` exists as a DNS zone but is not serving yet.

## Where the Python client stands (end of 2026-10-07 session, part 2)

**Working, verified live:**
- full native join: RUPP+QUIC, app=4 channels, early-auth, A7 → 90 → 92 → 8A → 8F
- server sends the full 1857-byte 0x93 join reply (byte-identical to the native's)
- **with an EMPTY A7 the server sends the 0x9B anti-cheat challenge** (1962–1978 B on
  app=4 chan=1): `[9b][u1 u32][u2 u32][len u32][blob]`
- the server accepts a *correct* answer: in an early native run the answer produced
  by the native for our patched challenge values got **"Assigned peer id = 44"**
  (replication start) on the native's own connection

**The one remaining unknown — what a correct answer does for a Python client:**
- The challenge `blob` is **constant per server build** (verified byte-identical across
  servers with equal message size); `u1`/`u2` are per-session.
- The native answers 9 B `[0x9b][u2][answer]` within ~15 ms; the answer is computed
  by the "challenge" provider (Luau VM: `sub_435D53A` → `sub_435D892` → `sub_435E556`
  → `sub_274DF88`), not by any simple hash of blob/u1/u2 (extensively tested: md5/sha/
  blake/xxh32/crc32/adler32 of many combinations, XOR/add relations, linear fit, ChaCha20
  decrypts, record reads — all negative).
- **Oracle solution implemented and working**: with two accounts and a live native client
  on the same server (blob-checked), `tools/oracle_patch.gdb` patches the native's
  challenge u1/u2 to the Python client's values, captures the computed answer, and
  `py/probe10.py` sends it within ~3 ms.
- Even with the correct answer sent in 3 ms, the server **resets the chan-1 stream
  (app error 0x106) ~2 ms later** — identical to the reset timing when no answer is sent,
  and identical to what a mismatched-blob answer sees. The reset is therefore *not* an
  answer-timeout or answer-validation effect on the Python path; some other server-side
  check (session/integrity, e.g. the A7 script-hash queue it validated first, or
  connection metadata not reproduced by the pure-Python client) rejects the session
  either way.

## Protocol implementation notes (do not regress)

- `0x8A` (join request): fully understood and rebuilt from our own ClientTicket +
  SessionId JSON (`build_8a` in `py/probe5.py`); its hash v31 = obfuscated
  xxh32(ClientTicket, seed=1) with the compile-time constant `0x71375635` — validated
  byte-for-byte against two independent captures.
- `0x90` (client info): must be rebuilt with OUR join reply's `joinTicket`
  (`SerializedClientFields` + `EncryptedServerFields`) and `RandomSeed1` +
  `APIsecurityToken` from OUR joinScript, **AND its 20-byte trailer must be preserved**
  (5×u32: `0xB1FB276E`, `0x51B1788E`, `E2`, `E1`, `0x228079AC`, where
  `0x63E25F26 = E2 ^ ((E1 & 0xFFFF) | 0x276E0000)`). `build_90` in `py/probe7.py`
  reproduces a captured 0x90 byte-for-byte (10713 B exact) from equivalent inputs.
- `0x92` nonce: `[92] + LEB(zigzag64((v8<<32) | (v8 ^ 0x63E25F26)))` with v8 a random u32.
- `0xA7` script-hash queue: `[a7][u16le count][count × 16-byte records]`; the records
  differ per session (client script state). The server validates them; an empty A7
  (`a7 00 00`) still gets the 0x9B challenge but never replication.
- Early auth: `a8 11 21 <33B> 42 <66B>` from ClientTicket parts 2/3 (base64-decoded).
- Server ctrl answers with app=4 OpenUnreliable channels {3,5,6,11} → wires {3,5,7,9}
  (allocation varies per session), then server-opened reliable streams for channels
  {0,1,2,4,7,8,9,10,12,13} (client sees stream headers `06 01 04 <chan u32be>`).
- The QUIC stream for the server's channel-1 data sometimes gets reset with app error
  `0x106` right after the 0x9B exchange; this is the server's final gate.
- **Only one client per account may be joined to the same place.** A second session on
  the same account causes stream resets that look like rejections — use a second account
  for parallel native+Python tests (`run/cookie.txt` / `run/cookie2.txt`).

### How it works (all steps verified against native ground truth)

1. **Wire blob → standard Luau bytecode** (`tools/standardize_wire.py`):
   Roblox's loader (sub_679992E) parses the wire file, then remaps each
   instruction's opcode byte through two tables in libroblox.so:
     - `byte_CC2904` (VA 0xCC2904, runtime-verified identical): wire_op -> internal_op
     - `byte_CC2A04` (VA 0xCC2A04): internal_op -> STANDARD Luau opcode number
   Instruction length: `sub_27509DA(v)` returns 2 iff
     (v-7) in [0,0x3B] and bit set in the literal `0x829400003F02323`, or
     (v-74) in [0,0x10] and bit set in the literal `0x00017E7B`
   (the `mov ecx, offset byte_17E7B; bt ecx, edi` tests the address constant,
   not memory!). Tables are dumped in `tools/roblox_bc_tables.json`.
   Result: every proto walks cleanly; operands byte-identical to the native's
   own post-remap code dumps (`run/remap`, `run/comb`). 24/24 protos, 899 starts.

2. **The decoded program runs in upstream Luau**, using the separate runner
   project `rbx_runtime/` (links the pristine `third_party/luau` submodule,
   pinned; nothing in the third-party checkout is modified):
   - `Random` is an exact port of Roblox's PCG (sub_27B30AE / sub_2307554):
       state = M*seed + C with M=0x5851F42D4C957F2D, C=0x399D2694695129DE,
       next = M*state + 105, out32(s) = ror32((s>>27)^(s>>45), s>>59),
       NextInteger small path: lo + ((out32 * (range+1)) >> 32).
     **Seed = xv + yv as the FULL 64-bit sum of the two unsigned 32-bit
     challenge fields** (verified: recovered seed == u1+u2 exactly, including
     carries above 2^32, e.g. 0x14b5e5848 -> native state 0x7740cff9389a6686).
     RNG streams match the native 20/20 draws in every checked session.
   - The program's arguments arrive as `(u2, u1)` — i.e. the SECOND challenge
     field is the first program argument (`xv`), the first is `yv`. (Both
     orders were tested; only this one matches.)
   - `game.JobId`, `bit32`, `newproxy`, `getmetatable/setmetatable`, `xpcall`,
     `tostring`, `os.exit` are provided by `rbx_runtime/src/main.cpp`.

3. **Environment checks** (the xpcall block at the end of the program) must
   match the native sandbox. Fitted from the data (constant per client build):
   - UserSettings() both calls succeed; `tostring(UserSettings())` byte-sum = **1924**
     (stacked 4182 = 1924 + (1924+334); any string with this byte sum behaves
     identically, e.g. "a"*19 + "Q")
   - `os.exit` missing -> +9001
   - `RunService:IsStudio()` false -> +1024
   - newproxy `__namecall` works -> +52
   With these, all five datasets match exactly. (With defaults "nope"/missing/
   false/ok the computed answers were off by exactly 0xCF2 = 3314 — the
   UserSettings difference.)

### ~~Still open~~ → SOLVED (2026-10-08): blob → program transform REVERSED

The wire blob transform (0x9B blob ~1950B → 7226B program) is fully static —
no session key. Reversed from `sub_274FA64` (libroblox challenge script loader):

1. **XOR keystream** from the blob's own first 4 bytes:
   - `key[i] = ((blob[i] ^ "RSB1"[i]) + [00,d7,ae,85][i]) & 0xFF`   (i < 4)
   - `plain[p] = blob[p] ^ ((41*p + key[p & 3]) & 0xFF)`   (all p)
   (native: xmmword_205C50="RSB1" xor, xmmword_2042D0 byte-add,
    per-16B-block `v6 += 0x90` == 41*16 mod 256; scalar tail `v11 += 41`)
2. **Validation**: the derived 4-byte key IS `xxhash32(plaintext, seed=0x2A)`
   (`sub_69FB2B0(v19, v26, 0x2A)` vs `v40`, mismatch → flag 0x40)
   ✅ passes on all 5 datasets
3. **Payload**: `u32 at [4:8]`: 0 → raw wire bytecode at [8:];
   else = uncompressed size, zstd frame (magic `28 b5 2f fd`) at [8:]
   (compared to `-47205080`, decompressed by `sub_6C2FB3A` = ZSTD_decompress)

Implemented in `tools/challenge_blob.py` (`decode_blob` / `blob_to_standard`;
pure-Python xxhash32 + libzstd via ctypes — no pip deps). Verified byte-exact:
decrypted+zstd output == native loader input on all 5 datasets.

**Complete autonomous path**: `0x9B blob → challenge_blob → standardize_wire →
challenge_runner → answer` — 2–7ms, no native/gdb/oracle anywhere.
`py/solve9b.py` wraps it (`solve_message(msg, job)`); `py/probe10.py
--source local` (default) answers live: challenge received → solve →
send `[9b][u2][answer]` on chan1.

## TLS custom extension 0xFF00 = CAPABILITIES exchange (2026-10-08, IDA+gdb)

**What it is**: an 8-byte little-endian **u64 capability bitmask** exchanged
during the TLS handshake (`RbxTransportQuicPeer` "custom TLS extension").
Server value = its `netStackConfig.caps` from the join reply (16-hex string of
the LE u64); e.g. server `022dd3ef52ff0892` ↔ ext bytes `92 08 ff 52 ef d3
2d 02`. Native client conn#0 sends `0x002dd3c750b70892` (bytes `92 08 b7 50
c7 d3 2d 00`) — a strict subset of the server's (server has extra bits);
conn#1 of the same session sends **8 zero bytes** → zeros are tolerated.

**Registration/flow (libroblox.so offsets, IDA instance)**:
- `OsslContext::vtable[6] = sub_6380F58` → `SSL_CTX_add_custom_ext(ctx,
  0xFF00, context=1152, add_cb=sub_638104F, free=0, add_arg=getter,
  {parse_cb=sub_638120C, parse_arg=setter})`. 1152 = 0x480 =
  `SSL_EXT_CLIENT_HELLO|SSL_EXT_TLS1_3_ENCRYPTED_EXTENSIONS` (send in CH,
  echo in EE).
- Client registers at `sub_63AB002` (getter=`sub_63A84E6`, setter=
  `sub_63A8522`), server at `sub_63ABA2C` (+extra `sub_63A9514`).
- add_cb calls the getter at **`0x63810A4 call r13`** (rax=ptr, rdx=len at
  `0x63810A7`); requires len<256 else alert 80.
- getter `sub_63A84E6`: reads tagged fn at `conn+0x4D8` / buffer at
  `conn+0x4C0`; the fn is `sub_638CEE2` → returns ptr to the **local caps
  u64** and logs `[FLog::RbxTransportQuicPeer] Sending custom TLS extension
  with capabilities: {}`.
- parse_cb `sub_638120C` **always returns 1 when configured** (app return
  ignored) → TLS-level acceptance never depends on content; logs `Received
  custom TLS extension of size {}`. setter `sub_63A8522` appends the bytes
  to a buffer at `conn+0x500`.
- receive side `sub_638CFB6`: caps valid **only if exactly 8 bytes** (else
  0), logs `Received remote peer capabilities: {}` then
  `Combined peer capabilities: {}` after `*combined &= remote`.
- negotiation (per `sub_63108C8`): common = local & remote; ext absent +
  `RbxTransportFailClosedCapabilityNegotiation` (byte_76EBDE8) OFF →
  common = local (optimistic); ON → 0. Server caps can also come from the
  join reply (`RbxTransportTakeServerCapabilitiesFromJoin`). Downstream:
  `Assigning capabilities {} to Replicator`,
  `pushProtocolNegotiatedCapabilities`, `Peer has capabilities: 0x%llx,
  common capabilities: 0x%llx`.
- C++ client: register custom ext 0xFF00 first (add first ⇒ appears first in
  ClientHello, matching native order), send 8-byte LE caps
  `0x002dd3c750b70892` (byte-identical to native conn#0; alternative if
  rejected: zeros, proven tolerated by native conn#1), parse cb stores/ignores.

gdb evidence: `run/extff00/index.txt` (GETTER=0x63A84E6, ctx vtable =
QuicClientConnection `0x70E88B0`, PAYLOAD#0/#1, PARSE#0/#1 server echo
`9208ff52efd32d02` for both conns), tooling `tools/extff00.gdb` +
`tools/extff00_round.sh`.

### Why Python never got accepted (the ~15ms window)

probe10's answer timeline on challenge=yes runs
(live_a7real_1.log): 0x93 at T, 0x9B challenge at T+362ms, **0x106
DisconnectSendPacketError stream reset at T+377ms**, Python answer at
T+393ms (29ms executor solve) — the server gave up **16ms** after sending
the challenge, i.e. before Python's answer could arrive. The in-process C++
solve is **1-2ms**, so the answer lands inside the window. This is the whole
game: the challenge→answer round trip must beat ~15ms.

### Corrupt-answer control (verified 2/2 — was the last open item)

`--corrupt` (answer ^= 0xDEADBEEF): the server still streams **exactly
63871B** (initial state) and then **CONNECTION_CLOSE → ERR_DRAINING at
+136/+137ms** (both runs byte-identical), instead of continuing replication.
Correct answer → open-ended stream (934KB-1.13MB runs). Proves the 0x9B
answer is exactly what is being validated. Caveat: the summary `peer=yes`
flag fires on any post-answer traffic, so it reads "yes" in corrupt runs too
— the discriminators are `err=` (ERR_DRAINING vs empty), resets, and
session lifetime.
